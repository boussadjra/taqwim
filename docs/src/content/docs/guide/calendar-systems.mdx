---
title: Hijri calendar systems
description: Choose Umm al-Qura, Civil or TBLA without changing Taqwim's date shape.
---

Taqwim uses **Umm al-Qura** (`islamic-umalqura`) by default. Existing code does
not need to change, and its conversions, range errors and component output keep
the same meaning.

The other built-in choices are deterministic tabular calendars:

| System      | Identifier         | Rule                                         | Range                                             |
| ----------- | ------------------ | -------------------------------------------- | ------------------------------------------------- |
| Umm al-Qura | `islamic-umalqura` | Taqwim's authoritative Saudi table           | 1343–1500 AH                                      |
| Civil       | `islamic-civil`    | Fixed 30-year arithmetic cycle, Friday epoch | Proleptic; `Date` output is limited by JavaScript |
| TBLA        | `islamic-tbla`     | The same arithmetic cycle, Thursday epoch    | Proleptic; `Date` output is limited by JavaScript |

Civil and TBLA alternate 30- and 29-day months. Month 12 gains a day in years
2, 5, 7, 10, 13, 16, 18, 21, 24, 26 and 29 of each 30-year cycle. TBLA's epoch
is one day earlier than Civil's, so the same Hijri fields identify different
absolute days.

These are arithmetic calendars. They are not observational calendars and do
not claim to reproduce local moon sightings. Taqwim does not expose plain
`islamic`, because that identifier does not select one exact algorithm. It also
does not expose `islamic-rgsa`: that identifier represents a Saudi sighting-based
calendar and must not be approximated with arithmetic or a fixed offset.

## Core

Optional algorithms have separate imports, so a default Umm al-Qura bundle does
not include them.

```ts
import { formatHijriDate, toGregorian, toHijri } from '@taqwim/core'
import { islamicCivil } from '@taqwim/core/calendars/islamic-civil'
import { islamicTbla } from '@taqwim/core/calendars/islamic-tbla'

toHijri('2026-08-30', { calendarSystem: islamicCivil })
// { hy: 1448, hm: 3, hd: 16 }

toGregorian({ hy: 1448, hm: 3, hd: 17 }, { calendarSystem: islamicTbla })
// Sun Aug 30 2026, local midnight

formatHijriDate({ hy: 1448, hm: 3, hd: 10 }, 'iD iMMMM iYYYY — yyyy-MM-dd', 'en', { calendarSystem: islamicCivil })
// "10 Rabi' al-awwal 1448 — 2026-08-24"
```

The same final `{ calendarSystem }` option is available on calendar-dependent
conversion, validation, month-length, weekday, arithmetic, business-day and
formatting helpers. Leave it out for Umm al-Qura.

## Calendar strategy contract

`HijriCalendarSystem` is a small, dependency-free strategy over integer epoch
days:

```ts
interface HijriCalendarSystem {
  readonly id: 'islamic-umalqura' | 'islamic-civil' | 'islamic-tbla'
  toEpochDay(date: HijriDateObject): number | null
  fromEpochDay(epochDay: number): HijriDateObject | null
  daysInMonth(year: number, month: number): number
  readonly minEpochDay?: number
  readonly maxEpochDay?: number
}
```

Parsing Gregorian input, constructing `Date`, formatting, grid generation and
navigation stay shared. A strategy only supplies calendar-specific date maths.
The components receive the strategy object, not an identifier looked up in a
global registry.

## Components

Every headless and styled calendar and date picker accepts the same optional
`calendarSystem` prop. The store uses that one strategy for headings, grids,
selection, navigation, validation and Gregorian secondary dates.

```vue
<script setup lang="ts">
import { islamicCivil } from '@taqwim/core/calendars/islamic-civil'
import { HijriCalendar } from '@taqwim/vue-styled'
</script>

<template>
  <HijriCalendar :calendar-system="islamicCivil" />
</template>
```

```tsx
// React
import { islamicCivil } from '@taqwim/core/calendars/islamic-civil'
import { HijriCalendar } from '@taqwim/react-styled'

;<HijriCalendar calendarSystem={islamicCivil} />
```

```svelte
<script lang="ts">
  import { islamicCivil } from '@taqwim/core/calendars/islamic-civil'
  import { HijriCalendar } from '@taqwim/svelte-styled'
</script>

<HijriCalendar calendarSystem={islamicCivil} />
```

```tsx
// Solid
import { islamicCivil } from '@taqwim/core/calendars/islamic-civil'
import { HijriCalendar } from '@taqwim/solid-styled'

;<HijriCalendar calendarSystem={islamicCivil} />
```

```ts
// Angular component
import { islamicCivil } from '@taqwim/core/calendars/islamic-civil'

calendarSystem = islamicCivil
```

```html
<taqwim-hijri-calendar [calendarSystem]="calendarSystem" />
```

Changing the prop at runtime rebuilds derived state without emitting a
selection change. A controlled numeric value is not rewritten if it is invalid
under the new system; the calendar reports its existing invalid state.

## Persist the system with the date

`{ hy: 1448, hm: 3, hd: 10 }` is not an absolute day unless its Hijri system is
known. If the fields themselves are the record, persist both:

```ts
{
  date: { hy: 1448, hm: 3, hd: 10 },
  calendarSystem: 'islamic-civil',
}
```

For an appointment or other absolute event, prefer storing its canonical ISO
Gregorian date and deriving the chosen Hijri presentation when rendering.

## Bundles and runtimes

`@taqwim/core` still has zero production dependencies. Its default entry only
includes Umm al-Qura; Civil and TBLA enter a bundle only when their explicit
subpaths are imported. Both optional variants share one small integer algorithm.

Node, Deno and Bun run the built ESM exports; Node and Bun also run CommonJS.
The runtime checks cover all three calendars in UTC, Riyadh and Los Angeles.
Conversion does not use `Intl`, so its result does not depend on locale, ICU's
Hijri data or the host time zone. As before, `toGregorian` returns local
midnight and `toHijri(Date)` reads local date parts.

## Migration

There is nothing to migrate for existing users. Omitting `calendarSystem`
continues to select Umm al-Qura everywhere.
